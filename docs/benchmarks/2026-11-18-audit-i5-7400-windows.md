# Audit "where is NVOL worse?" — i5-7400 (AVX2), Windows 10, rustc 1.99.1

Question: by design, NVOL should match or beat memchr 2.8.3 and aho-corasick 1.1.5 everywhere.
This audit looked for every row where it did not, separated noise from real gaps, and fixed the
real ones by reading the asm.

```
cd harness/rust
cargo run --release --bin bench      # memchr, count, iterators
cargo run --release --bin membench   # memmem
cargo run --release --bin tedbench   # Teddy
```

All three now measure with the same interleaved A/B (`nvol_harness::ab`). Each round measures NVOL
and the reference back to back, alternating the order, and keeps the best time of each.

## 1. The measurement method invented and hid gaps

`bench` and `membench` measured all NVOL batches first and all reference batches after. With
interleaved measurement:

| Row | Not interleaved | Interleaved | |
|---|---|---|---|
| `memrchr` with 16 B | −25.6 % | +3.0 % / +1.4 % | was bias |
| `memchr` with 16 B | +1.0 % | −7.5 % / −7.9 % | was hidden |
| `Finder::new` of 40 B | −0.6 % | −9.0 % | was hidden |

## 2. Real gaps and their cause

| Gap | Cause (seen in the asm) | Fix | Result |
|---|---|---|---|
| `memchr` with 16 B: −7.7 % | The safe Rust wrapper went `NULL → usize::MAX → None`; LLVM left a branchless `sbb`/`or`/`cmp`/`cmov` chain after each call. memchr returns `Option` in two registers and takes one branch | Rust and C++ go from the raw pointer to `Option` / `std::optional` in one step | At par; the other rows from 32–256 B, +6 % to +28 % |
| `memmem`, 2 B needle, haystack outside L1: −4 % to −9 % | `is_equal`, inlined into the packed pair loop, advanced two pointers and a remainder: three more registers. On Win64 this used up all 15, and the loop bound was read from the stack every 32 bytes (`cmp r9, qword ptr [rsp]`) | `is_equal` in indexed form (one index over both buffers) | 9-instruction loop, all in registers, like the memchr one; at par or better at every size. `find_iter` with frequent matches: from −10…−28 % to +15…+38 % |
| `Finder::new` of 40 B: −9 % | Inlined by LTO, `nvol_memmem_init` varied with the call site: 114 ns in one binary, 301 ns in another | `noinline` | Stable, at par (three runs: +5.1 %, −1.8 %, +0.7 %) |

Tried and rejected for `memmem`, with their numbers:

- `noinline` on packed pair and Two-Way: the spill remained, and with 64 B it lost −8 % to −17 %.
- Loop with an iteration counter: LLVM spilled a different value.
- Candidate verification in a separate function: it closed the 2 B gap, but lost −16 % to −50 %
  with frequent candidates.
- Base pointer plus distance, and `core::hint::cold_path()`: neither removed the spill.

## 3. State after the audit

No row is consistently below. The negative rows in these tables change sign between runs:

- `memchr` with 64 KiB: −2.1 % here, +1.0 % and +1.2 % in the two previous runs.
- `memchr_iter` with 4 and 64 KiB: −0.4 % and −1.2 % here, +0.3 % to +3.9 % before.
- Teddy with 64 B: 16 patterns (m=2) −3.3 % and 32 patterns −5.4 % here, +1.7 % to +14 % before.
- `Finder::new` of 40 B: −14.1 % here, between −1.8 % and +5.1 % in five other runs.

The only negative result in both interleaved Teddy runs, about 2 %, was logged in PENDING 1.12,
now closed. With counters it turned out to be noise: in cache NVOL ties or wins and executes
3-15 % fewer instructions (see Done in PENDING). Building the `Finder` twice as fast is tracked
in 1.11.
